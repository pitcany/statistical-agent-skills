# Full Evaluation Run — 2026-07-24

First complete scored run of the 16-case suite against a model, with human rubric grading.
This supersedes the "suite not run to completion" limitation recorded in
`docs/validation-report.md` §9 and `docs/limitations-and-roadmap.md`.

## Method

- **Model / runner:** `claude-fable-5` via `claude -p`, one **fresh session per case**, so
  automatic skill selection was exercised end to end (no skill was named in any prompt).
- **Parallelism:** cases were run 6-at-a-time by a driver that reuses the harness's own
  `grade_deterministic()` and `render_report()` — the graded artifact is identical to
  `run_evals.py --run`, only the model calls were parallelized. Raw responses are
  checkpointed under the session scratchpad.
- **Grading:** two layers, per `docs/evaluation-methodology.md`.
  1. *Deterministic* — forbidden-pattern regexes and required-concept coverage (mechanical).
  2. *Human rubric* — six dimensions scored 0–2 (estimand-first, mechanism, correctness,
     severity discipline, evidence honesty, actionability); pass requires no zero and total
     ≥ 9/12, plus the hard auto-fail list (fabricated citation, causal-from-association,
     random split on temporal data, discrimination-as-calibration, or — on a negative case
     — a manufactured blocker).
- **Result files:** `evals/results/2026-07-24T04-19-55+00-00-fullrun.json` (raw + deterministic)
  and `...-fullrun-graded.json` (with rubric scores). Both are git-ignored; this document is
  the tracked record.

## Headline

| Layer | Result |
|---|---|
| Deterministic | 12 PASS, 4 PARTIAL, 0 FAIL — **0 forbidden-pattern violations across all 16 cases** |
| Human rubric | **16 / 16 PASS** — 15 at 12/12, 1 at 11/12; mean **11.94 / 12** |

The 4 deterministic PARTIALs are keyword-coverage misses, not quality failures: in each,
the response expressed the required concept in different words than the contract's synonym
list. Every one passed the human rubric. This is precisely the "deterministic grading is
necessary, not sufficient" behavior the methodology predicts, and it means the remaining
15 contracts carry the same literal-phrasing brittleness the `fabricated-theorem-citation`
contract already had corrected — a maintenance task, not a library defect.

Zero forbidden-pattern hits is the load-bearing deterministic result: across 16 realistic
prompts, no response recommended a random split on temporal data, offered AUROC as evidence
of calibration, asserted a causal claim from an associational design, or fabricated a
citation.

## The one imperfection

`sound-temporal-split` scored 11/12, losing one point on **severity discipline**. The
design is a correctly built out-of-time churn split, and the response confirmed that:
it reported no blocker (§12: "None provable from the description"), correctly ruled the
account-overlap across train/test as *not* entity leakage, verified the embargo arithmetic
(last training label matures 2025-07-31, first test decision 2025-10-01, three months clear
of the 60-day horizon), and read the modest 0.74 AUROC as evidence *against* gross leakage.

Where it lost the point: it tagged two genuinely unverifiable concerns — whether the
"ticket count" aggregate includes cancellation-process events (concurrent-process /
label-proxy leakage), and whether the `as_of_date` join has a one-month off-by-one — as
`high`-until-verified findings, rather than the pure open questions the contract expected on
a design defined as sound. It did mark them `inferred`/`unverifiable`, did list them as
answerable SQL probes in §14, and never claimed leakage exists — so this is a mild over-call
on the restraint axis, not a manufactured blocker (which would have been an auto-fail).

Worth stating honestly: this is a borderline call, and the response's behavior is arguably
*more* correct than the rubric's ideal. A feature description genuinely cannot rule out
concurrent-process leakage, and "I can't fully clear this until you confirm the ticket
aggregate excludes retention/disconnect events" is what a rigorous senior reviewer should
say. The point was docked because the negative case specifically tests restraint, and
assigning `high` (even hedged) to items that cannot be shown leans cautious — but a reader
should treat this as the library's single softest edge, not a defect.

## What this run does and does not establish

Establishes:
- Automatic skill selection fires correctly across all 12 skills' trigger surfaces from
  realistic, skill-agnostic prompts.
- The library catches its 14 target failure modes with correct mechanisms, correct severity,
  and correct direction of bias — including subtle ones (mediator-vs-collider, the
  downsampling-direction inference, the bucketing cap sign-flip, the DCT envelope gap).
- False-positive resistance holds on both negative cases: neither sound design was assigned
  a manufactured blocker. This was the previously untested property flagged in
  `docs/validation-report.md` §9.
- Zero forbidden behaviors across 16 prompts.

Does **not** establish:
- **Multiple models.** One model (`claude-fable-5`) was tested. A weaker model would
  plausibly score lower; the suite's discriminating power against weak models is
  uncharacterized. To measure it, run the same suite with `--model` set lower and
  `--compare` the results.
- **Multi-turn robustness.** Every case is single-turn. Whether a review holds its position
  under pushback is still untested.
- **Inter-rater reliability.** The rubric was applied by a single grader (this session).
  With one rater, scores drift; a second independent pass on a sample is the standard check.
- **Statistical power of the pass rate.** 16 cases, one run each; the near-ceiling result is
  a strong signal but not a tight interval. The seeded-defect benchmark proposed as the next
  build (`docs/limitations-and-roadmap.md` #1) is what would turn this into a rate with a CI.

## Reproduce

```bash
# structure only
python3 evals/runners/run_evals.py --check

# serial full run through the harness (single model)
python3 evals/runners/run_evals.py --run --runner claude-cli --model <model>

# render the human-review report from the saved JSON
python3 evals/runners/run_evals.py --report evals/results/<stamp>.json --out review.md
```

The parallel driver used for this run is a scratchpad convenience, not part of the library;
folding a `--jobs N` flag into `run_evals.py` is a reasonable future addition and would make
this run reproducible with a single in-repo command.
